1. Evidence-to-decision flow

Design intent, partially implemented: Separate technical definitions, operating history, documented intent, and owner knowledge before proposing a change. XML inventory, durable artifacts and review exist; all owner/evidence gates and general approved artifact generation shown here are not yet a complete execution path.

On small screens, scroll horizontally. Labels remain at a readable size without automatic word wrapping.

System analysisHuman input or reviewDurable evidence or gated output

Figure 1 status: Arrows describe required evidence and approval relationships, not proof that all sources were collected or every gate ran. Approved artifact generation here is the target general factory, not the narrow SQL draft or demonstration path.

  1. Register evidence: Preserve original files and document status, versions, dates, environment, and authority.
  2. Separate operational dimensions: Enabled state, scheduling, observed usage, declared lifecycle, and approved migration scope are distinct.
  3. Ask rather than guess: Missing or conflicting facts create assigned questions and block only dependent decisions.
  4. Explain each change: Cite facts and counterevidence, compare alternatives, state invariants and blast radius, and attach acceptance tests.
  5. Approve explicitly: Scope/design, retirement, artifacts, and deployment are separate decisions. Original inventory is preserved.

2. Supervised agent interaction

Design intent with implemented advisory core: Specialists return typed findings. Actual architecture/supervisor redesign submissions and version review exist. The complete independent artifact/release chain remains planned; the supervisor does not acquire execution permission from this diagram.

Two specialist roles per row keep the flow compact. Arrows carry requests and findings, not unrestricted shared chat.

Figure 2 status: The arena renders actual recorded events, with unknown role activity left unknown. It is not a replay of every arrow here. Review approval is version-specific and outline-only; no generic executable generation or deployment permission follows.

  1. Delegate: A request names the task, object IDs, input/evidence versions, unresolved questions, output contract, tools, and budget.
  2. Return: Each role submits cited findings, assumptions, conflicts, tests, and status. Missing information is a valid result.
  3. Reconcile: The supervisor validates results and prepares the next scoped context. An agent cannot erase another role's conflicting finding.
  4. Intervene: Owners answer assigned questions. The service records authority and scope, versions the evidence, and resumes affected tasks.
  5. Gate: Human approval and deterministic checks freeze a proposal snapshot before executable artifact generation. Artifact/deploy reviews follow separately.
